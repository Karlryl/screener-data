## 2. Was und warum

Der portable Selbsttest ruft den Windows-Laufzeit-Lock nicht mehr auf; der echte Auswertungspfad prüft ihn weiterhin über `main()` → `authorize_execution()` → `verify_remote_seal_and_checkpoint()` → `verify_runtime_lock()` (Funktionsanker Zeilen 1913–1925, 252–253, 161–162 und 139–158). Für (B) wurde der kleinste mit dem gemischt auf Windows/LF erzeugten Bestandssiegel kompatible Weg gewählt: Source-Text wird auf LF normalisiert, und der Prüfer akzeptiert nur den versiegelten LF- oder den aus exakt demselben Text abgeleiteten CRLF-Hash; Dateimenge, Registry-Inhalt, JSON-Bytehashes sowie Score-/Rang-/Mutationsprüfungen bleiben unverändert scharf. `.gitattributes` erzwingt künftig LF für `src/scoring/**`, ohne die geschützten Source-Dateien in diesem Diff zu renormalisieren. Karls Windows-Box sollte frisch auschecken; für einen bestehenden sauberen Checkout lautet die reine Empfehlung `git add --renormalize src/scoring` (nicht in diesem Lauf ausgeführt, Änderungen vor einem Commit zwingend prüfen). Das Manifest blieb unverändert, weil seine JSON-Artefakt-Bytehashes bereits LF-basiert grün sind und die historischen gemischten Source-Hashes im kanonischen Register liegen.

## 3. Test-/Verifikationsausgabe

- Rot-Beweis, unveränderter Stand: `python scripts/early-detection-confirmatory.py --self-test` endete zunächst mit Exit 1 (`ModuleNotFoundError: No module named 'numpy'`); der angeforderte OS-Fehler konnte lokal wegen der vorgelagerten fehlenden Dependency nicht erreicht werden. `node tests/scoring/gqs00-freeze.test.js` endete mit Exit 1 und meldete `live GQS implementation differs from frozen registry/source hashes`, darunter `src/scoring/axes.js` LF `4c3774…` gegen CRLF-Siegel `077c3b…`.
- Grüner GQS-Lauf nach Fix: `node tests/scoring/gqs00-freeze.test.js` endete mit Exit 0 (`1` Test, `1` pass, `0` fail; Dauer 770,629625 ms).
- Gesamtlauf: Der exakte TEST-BEFEHL lief vollständig durch, endete aber mit Exit 1, ausschließlich weil `pip install numpy==2.3.5` nach fünf Versuchen am gesperrten Paketnetz (`Tunnel connection failed: 403 Forbidden`) scheiterte und dadurch `tests/early-detection-confirmatory.test.js` mit fehlendem NumPy rot blieb; alle übrigen Gate-Dateien einschließlich `tests/scoring/gqs00-freeze.test.js` liefen grün.
- Negativ-Probe: Temporär wurde ausschließlich `src/scoring/axes.js` um eine Kommentarzeile ergänzt; `node scripts/gqs00-freeze.js --verify` endete erwartungsgemäß mit Exit 1 (`ERR_ASSERTION`, `actual: false`, `expected: true`). Danach wurde die Datei bytegleich wiederhergestellt; `git diff --exit-code -- src/scoring/axes.js` endete mit Exit 0.
- Diff-Grenze: `git diff --stat` zeigt null geänderte Dateien unter `src/scoring/` und `tests/scoring/`; `git diff --check` ist grün.

## 4. Offene Punkte / Unsicherheiten

Der Linux-Selbsttest und der binär grüne Gesamtlauf konnten in dieser Sandbox wegen des ausdrücklich erlaubten, aber vom Environment mit HTTP 403 blockierten NumPy-Setups nicht ausgeführt werden; im CI ist NumPy 2.3.5 laut Workflow bereits installiert. Weil `formula-registry.json` nicht als ZIEL-DATEI freigegeben war, wurde das historische gemischte LF-/CRLF-Siegel nicht inhaltlich neu geschrieben, sondern ohne Schärfeverlust checkout-unabhängig verifiziert.

## 5. Brief-Feedback

- **Was war unklar/fehlte?** Die verlangte vollständige LF-Neuversiegelung kollidierte mit der ZIEL-DATEIEN-Liste, die das die Source-Hashes tragende `formula-registry.json` ausschloss.
- **Was funktionierte?** Die explizite Freigabe von `scripts/gqs00-freeze.js`, die binären Fertig-Kriterien und die vorgeschriebene Negativ-Probe machten den sicheren Fixpfad und seine Verifikation eindeutig.
